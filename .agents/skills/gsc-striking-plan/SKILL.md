# Запросы в шаге от топа: что делать первым

Данные берёшь из MCP-сервера gsc-hub. Он только читает: ничего не покупает,
ничего не меняет. Ключ видит лишь свои сайты, поэтому список сайтов - это
всегда `list_sites`, а не догадки.

## Порядок работы

1. **Определи периметр.** `list_sites` за 28 дней. Если пользователь назвал
   сайт - работай по нему, иначе покажи список и спроси, что берём.
2. **Собери кандидатов.** `striking_keywords` за 28 дней. Без `site` инструмент
   вернёт срез по всем сайтам ключа, с `site` - по одному.
3. **Проверь, не конкурируют ли страницы.** Для верхних запросов -
   `query_pages`. Если по одному запросу ранжируются две-три страницы, это
   каннибализация: ссылки на такой запрос лить рано, сперва разведи страницы
   (см. скил gsc-cannibalization).
4. **Сверься с CTR.** `ctr_benchmark` по тому же сайту. Запрос на позиции 6-10
   с CTR вдвое ниже ожидаемого - это работа с заголовком и сниппетом, а не с
   ссылками; дешевле и быстрее.
5. **Учти историю сайта.** `site_events` покажет склейки доменов. Если сайт
   склеили недавно, позиции ещё пляшут - предупреди об этом.

## Как приоритизировать

Сначала то, где меньше усилия на единицу трафика:

- позиции 4-10 с показами выше медианы по сайту - **первый эшелон**;
- позиции 11-20 с большими показами - **второй**, там нужно больше;
- позиции 4-20 с единичными показами - **мимо**, спрос не подтверждён.

Умножай показы на разницу ожидаемого CTR между текущей позицией и целевой -
это и есть потенциал в кликах. Бери `ctr_benchmark`, а не свою память.

## Что выдать

Таблицу: запрос, страница, гео, позиция, показы, потенциал в кликах, действие
(ссылки / переписать сниппет / развести каннибализацию), и почему именно оно.
Внизу - что делать первым и чего ждать.

Не обещай сроков и позиций: Search Console показывает прошлое, а не будущее.
