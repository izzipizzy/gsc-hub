Локальный self-hosted мульти-аккаунт хаб для **Google Search Console**. Подключаешь несколько Google-аккаунтов через OAuth, видишь все Search Console сайты в одной таблице, агрегируешь ключи и страницы поверх аккаунтов, дашборд карточек по сайтам с sparkline-графиками и дельтой к предыдущему периоду, по клику на ключ — 16-месячная история позиции. С версии 0.6.0 в коробке ещё и полноценный **набор SEO-аналитики** — деталка по каждому сайту (striking distance, каннибализация, CTR-бенчмарк, content decay, branded-разбивка, site health) и портфельный вид сразу по всем сайтам — плюс Bing/IndexNow и опциональный мульти-юзер-логин. С 0.8.0: графики трафика с апдейтами Google и твоими событиями по сайтам, машинный API с областью по сайтам и встроенным **MCP-сервером** для ИИ-агентов, опциональная покупка ссылок прямо из таблиц striking distance. Никаких внешних сервисов: данные Search Console остаются на твоей машине (исключение - покупка ссылок: выбранные запрос и URL уходят провайдеру, которому платишь). В SQLite лежат OAuth-токены, твои настройки и пара кешей, но не метрики Search Analytics; аналитика читается живьём, с коротким кешем в памяти.

Сделан как личная альтернатива seogets-style SaaS-инструментам, когда у тебя несколько Google-аккаунтов (личный, рабочий, клиентские) и не хочется логиниться в каждый Search Console отдельно.

> **Статус:** рабочий MVP, используется ежедневно на macOS. В коробке деплой через Docker Compose + OrbStack на `https://gsc.local`. Аккаунты подключаются через `http://localhost:5173`, потому что Google не принимает OAuth-redirect на `.local`-домены (см. [Деплой](#деплой-через-docker-compose--orbstack)).

## Возможности

### Мульти-аккаунт OAuth
- Подключай произвольное количество Google-аккаунтов. Каждый клик на **Connect Google account** запускает обычный Google consent flow (`webmasters` read-write scope, `access_type=offline`, `prompt=consent`). Read-write scope нужен для отправки sitemap'ов; если нужен только доступ на чтение — верни в `src/auth.ts` `webmasters.readonly`.
- Токены хранятся в локальном SQLite-файле (`./data/gsc-hub.db`). Refresh-токены ротируются автоматически; access-токены обновляются прозрачно за 60 секунд до истечения.
- Отозванные токены детектятся первым 401 от Google: аккаунт помечается как `revoked`, UI просит переподключиться, никаких тихих сбоев.

### Объединённая таблица сайтов (`/properties`, в UI **Sites**)
- Все Search Console properties со всех подключённых аккаунтов в одной full-bleed таблице.
- Live-аггрегат на каждый сайт за выбранный период: **Clicks / Impressions / CTR / Avg Pos**, плюс колонка **CSV export** (queries или pages, период настраивается).
- **Строка итогов** над таблицей суммирует **Sites / Impressions / Clicks** по всем не скрытым сайтам за выбранный период.
- Сортировка и фильтр через URL: `?days=1|3|7|28|60&sort=clicks|impressions|ctr|position|site|account&dir=asc|desc`. Bookmark, шаринг, browser-back работают как ожидаешь.
- **Бейдж «G»** рядом с каждым сайтом открывает поиск Google `site:` для быстрой ручной проверки индексации.
- Скрывай сайты, которые не нужны. Список хранится в SQLite, поэтому одинаков во всех браузерах, а массовые действия скрытые сайты пропускают.
- Domain properties отображаются как `example.com` (префикс `sc-domain:` GSC обрезается для UI, ссылка по-прежнему ведёт на `https://example.com/`).
- Клик по строке сайта разворачивает быстрый отчёт **URL Inspection** для топ-10 URL'ов (verdict, coverage, robots, last crawl, mismatch canonical). Использует Google URL Inspection API; дневная квота 2000 на Google-аккаунт. Результаты **кешируются на 12 часов** в SQLite (ключ: account + site + хэш url-набора). Повторный клик берёт из кеша; кнопка **Force refresh** — обновить с нуля. Кеш нужен потому что URL Inspection имеет жёсткий лимит 2000 вызовов/сутки на Google-аккаунт. Для сайтов без impressions или с малыми impressions в текущем периоде используется fallback по **sitemap**: gsc-hub спрашивает у Search Console какие sitemap'ы сабмиттил сайт, скачивает первый (с обработкой sitemapindex), и берёт до 10 URL'ов оттуда. Главная всегда включается.

### Отправка карт сайта (Sitemap submit)
- Кнопка **Submit sitemap** на каждый сайт: переотправляет в Search Console все уже зарегистрированные sitemap'ы, а если их нет — пробует угаданный `/sitemap.xml`. Inline-статус (`✓ N` / причина ошибки в подсказке).
- Кнопка **Submit all sitemaps** в тулбаре: параллельно по всем видимым (не скрытым) сайтам, с прогрессом и итоговой сводкой.
- Требует read-write scope `webmasters` (см. Мульти-аккаунт OAuth).

### Top queries (агрегированные, сортируемые)
- Агрегат по ключам поверх всех видимых (не скрытых) сайтов за выбранный период, с разбивкой **query × page × country**. Clicks, impressions, CTR (вычисляемый), Avg Pos (взвешенный по impressions).
- Клик по ячейке позиции открывает **Google SERP** для этого ключа в соответствующей стране.
- Клик на строку разворачивает **inline-график 16-месячной истории** для этого ключа: красная линия позиции + синие столбики impressions, gridlines, подписи диапазона. Агрегация по дням только по видимым сайтам.
- Client-side сортировка по столбцам (Query / Clicks / Impressions / CTR / Avg Pos), независимо от сортировки таблицы сайтов.

### Top pages (агрегированные, сортируемые)
- Тот же паттерн что и Top queries, но на уровне URL страниц. Полезно для поиска страницы, которая дала всплеск трафика.

### Аналитика по сайту (`/properties/[site]`)
Проваливаешься в отдельный property для полного SEO-разбора. Вкладки:
- **Striking Distance** — ключи на позициях 4–20 с реальными impressions: самые быстрые выигрыши в топ-10.
- **Keyword Cannibalization** — ключи, где конкурируют несколько твоих собственных URL, с чётким разбором winner/loser.
- **CTR Benchmark** — твой фактический CTR по позициям vs industry-reference кривая, плюс страницы, которые её недобирают.
- **Content Decay** — страницы, теряющие clicks **или** impressions относительно предыдущего периода.
- **Branded vs non-branded** — разбивка трафика с редактируемыми brand-терминами на каждый сайт.
- **Site Health** — SSL (срок / issuer / grade), Google Safe Browsing и Core Web Vitals (PageSpeed Insights, mobile). Запускается по требованию, кешируется на сайт. Нужен Google API-ключ (см. [Конфигурация](#конфигурация)); без него вкладка скрыта.

Все вкладки считаются live из Search Console; ничего не сохраняется кроме редактируемых brand-терминов и кеша health.

### Портфельная аналитика (`/properties/striking`, пункт **Portfolio** в меню)
Те же срезы сразу по всем не скрытым сайтам, из одного query-fan-out:
- Вкладки **Striking / Cannibalization / CTR / Branded / Decay**, все **адресуемые через URL** (`?tab=`).
- **Фильтр по стране (Geo)** и **copy-queries-to-clipboard**, оба учитывают текущий фильтр.
- Для каждой decaying-страницы — **статус индексации** через URL Inspection API, со прямой ссылкой в inspection-панель нужного Google-аккаунта.
- Async-стриминг (оболочка рендерится сразу) плюс короткий in-memory кеш результата, поэтому повторные открытия и переключения периода мгновенны.

### Графики трафика и события сайтов
- На странице сайта полный график трафика (клики, показы, позиция) с полосами **апдейтов Google** из публичного статус-фида Google.
- Страница Sites начинается с **пульса портфеля**: все видимые сайты, сложенные по дням, на тех же полосах апдейтов.
- **События сайта** - твои отметки на таймлайне: склейки доменов (донор → сайт), переезды, что угодно. Добавляются и удаляются на странице сайта, видны на графиках и карточках дашборда. `/events` - все события одной таблицей с фильтром по типу. Покупки ссылок добавляются автоматически из истории Magiclinks: одна фиолетовая отметка на заказ и сайт, количество, провайдер и переход в заказ. Дата — день покупки (UTC), а не публикации; старые заказы тоже видны, миграция не нужна.

### Bing Webmaster + IndexNow
- Данные производительности Bing рядом с GSC, с объединённым GSC/Bing keyword-роллапом.
- **Отправка sitemap в Bing** и **пуш URL'ов в IndexNow**, плюс индикатор наличия IndexNow-ключа на сайт.
- Требует `BING_API_KEY` (см. [Конфигурация](#конфигурация)).

### Машинный API (`/api`)
- Ключи API создаются на `/api`. Ключ показывается один раз, в базе хранится только его sha256. Каждый ключ можно ограничить списком сайтов - остальное для него не существует (`404`, а не `403`).
- `GET /api/v1/sites`, `/queries`, `/query-pages`, `/properties`, `/countries`, `/site-countries` отдают скрипту или серпмонитору те же цифры, что видны в интерфейсе. `POST /api/v1/site-events` записывает склейку.
- Документация для агентов отдаётся на `/api/v1/doc.md` (по ключу).

### MCP-сервер и скилы для агентов

- Встроенный **MCP-сервер** на `/api/v1/mcp`: Claude Code, Claude Desktop, Cursor
  и любой клиент со Streamable HTTP читают данные Search Console напрямую.
  Девять инструментов, **только чтение** - сводка по портфелю, запросы сайта,
  страницы по запросу, striking distance, каннибализация, CTR-бенчмарк,
  просадки, разбивка по странам и склейки доменов.
- **Ключ выдаётся на выбранные сайты.** Ключей может быть сколько угодно:
  создаёшь на `/api` и отмечаешь property - агенту на один пул, подрядчику на
  один сайт. Всё вне области невидимо: в списках не появляется, на прямой
  запрос отвечает `404`. Ключ без отметок видит все сайты, как было до
  появления областей.
- MCP ничего не пишет: ни склеек, ни покупок, ни правок, поэтому агент через MCP
  ничего не изменит и не потратит денег. Но сам ключ не только на чтение: тот же
  Bearer принимает REST-ручка `POST /api/v1/site-events`, которая записывает
  склейку на сайт из области ключа. Раздавай ключи с учётом этого.
- **Четыре скила** идут в комплекте (план по striking, каннибализация, разбор
  просадки, обзор портфеля). Тот же сервер отдаёт их промптами -
  `/mcp__gsc-hub__gsc-striking-plan` в Claude Code - и файлами на
  `/api/v1/skills`, так что для установки нужен ключ и адрес, а не копия
  репозитория. Подробности: [docs/MCP-SETUP.md](docs/MCP-SETUP.md).

```bash
claude mcp add --transport http gsc-hub https://your-hub.example.com/api/v1/mcp \
  --header "Authorization: Bearer gsk_your_key"
```

### Покупка ссылок (MagicLinks, опционально)
- Посты со ссылками на страницы в striking distance покупаются прямо из таблиц striking (портфельной и на странице сайта): отметил строки, получил расчёт, оплатил. Поддерживаются два провайдера, окно покупки по умолчанию выбирает того, у кого больше баланс:
  - **FieldLink** - покупка в два шага (задание → расчёт → заказ), сумма из расчёта перепроверяется при отправке заказа. [Регистрация](https://seoboost-root.info/r/flt_czhTpL1GKPqQXI2h1c463ULMS2IEzV6fjJow2hiGlMg) (партнёрская ссылка), затем ключ API в кабинете.
  - **369Team** (`magiclinks.online`) - покупка в один шаг, деньги списываются при создании заказа; цена перепроверяется прямо перед ним. За регистрацией и ключом - в Telegram [@links_369](https://t.me/links_369).
- На `/magiclinks` - ключи обоих провайдеров, балансы и все заказы с провайдером, прогрессом и (у FieldLink) статусом индексации; каждый заказ открывается до позиций и URL публикаций, с выгрузкой в CSV.
- Данные сервисов не кешируются: заказы и статусы читаются живьём. Хаб хранит только ключи и след покупок (какие пары «запрос + URL» уже куплены), чтобы таблицы striking их отмечали.
- По умолчанию ничего не включено: без ключа функция не мешает.
- Раскрытие: обе интеграции партнёрские. Ссылка на регистрацию в FieldLink - реферальная, а запросы к 369Team несут реферальный ID автора (`X-Referal-ID`).

### Опциональный логин и роли
- **Выключено по умолчанию** — тул остаётся single-user и loopback-only. Задай `ADMIN_EMAIL` / `ADMIN_PASSWORD`, чтобы включить форму логина, серверные сессии (пароли захэшены argon2), страницу управления пользователями и роли (**admin** / **manager**) с per-owner скоупингом аккаунтов.
- Нужно когда выставляешь приложение за пределы `127.0.0.1`; безопасные куки включаются автоматически, как только `ORIGIN` начинается с `https://`.

### Dashboard (`/dashboard`)
- Отдельный блок **«Сегодня»**: текущий день по времени Search Console, ещё набирается, поэтому ни с чем не сравнивается.
- Сетка карточек по сайтам: account label, домен, sparkline дневных кликов за текущий период, четыре метрики с **дельтой к предыдущему периоду той же длины** (например, последние 7 дней vs предыдущие 7 дней). Зелёный/красный, плюс знак `+` / `−` чтобы colour-blind пользователи видели сигнал.
- Конфигурируемая плотность: **2 / 4 / 6 колонок** через URL `?cols=`. Тот же period filter что и на Sites.
- Стабильный порядок при перезагрузке (clicks desc, tiebreaker по impressions, потом alphabetically).

### CSV экспорты
- Queries или pages, последние N дней (соответствует period filter), безопасное имя файла. Стримит `text/csv; charset=utf-8` с `Content-Disposition: attachment`. Скачивается с `/properties/export?account=...&site=...&days=...&dim=query|page`.

### Operator-grade UX
- **Sparklines** дневных кликов на карточках сайтов.
- **Privacy Blur** — один клик размывает PII (email'ы, домены, метрики) для скриншотов и шэринга экрана.
- **Refresh** сохраняет всё URL-состояние (period, sort, dir, cols) через SvelteKit `invalidateAll()`. Никаких `<form method="POST">` redirect-танцев.
- Все числа в таблицах — tabular-nums для вертикального выравнивания.
- Лёгкий hover на строках. Сортируемые заголовки показывают ↑ / ↓.
- **Короткий кеш в памяти.** Ответы Search Console держатся в памяти процесса до 60 минут, поэтому переходы быстрые и квота живёт дольше; **Refresh** сбрасывает кеш, рестарт начинает с нуля. Ответы Search Analytics в базу не попадают; исключения на диске (кеш URL Inspection, купленные пары «запрос + URL») - в разделе [Приватность](#приватность-и-данные).
- Никаких background-задач, cron, очередей, email-рассылок.

## Quickstart

Требования: **Node 22+**, **pnpm**.

```bash
git clone https://github.com/izzipizzy/gsc-hub.git
cd gsc-hub
pnpm install
pnpm dev
```

Открой <http://localhost:5173> — при первом запуске откроется **setup-визард** и попросит Google Client ID/Secret; `AUTH_SECRET` генерится автоматически, руками `.env` править не нужно. (Копировать `.env.example` в `.env` не обязательно — это нужно только для автодеплоя/CI, см. [Конфигурация](#конфигурация).) Кликни **Connect Google account**, пройди consent, повтори для каждого аккаунта.

Для постоянного локального деплоя используй Docker Compose — см. [Деплой через Docker Compose + OrbStack](#деплой-через-docker-compose--orbstack).

> **Подключай аккаунты через `http://localhost:5173`, а не `https://gsc.local`.** OAuth-политика Google отклоняет redirect на `.local`-домен (`Error 400: invalid_request`). Compose-конфиг специально пробрасывает loopback-порт, чтобы consent-flow шёл через localhost; повседневно можно пользоваться `https://gsc.local`. БД общая, поэтому токен, полученный на localhost, работает и на `gsc.local`.

### Быстрый старт (setup-визард)

1. `docker compose up -d --build`
2. Открой приложение (`http://localhost:5173` — для подключения Google-аккаунтов).
3. Автоматически откроется **setup-визард**: вставь Google **Client ID** и
   **Client Secret** (на странице показан точный redirect URI для GCP), выбери
   режим доступа (только loopback или наружу с логином) и сохрани. Руками
   `.env` править не нужно — `AUTH_SECRET` генерится сам и хранится в SQLite.

Если приложение будет доступно с других машин, задай `GOOGLE_CLIENT_ID`,
`GOOGLE_CLIENT_SECRET`, `ADMIN_EMAIL` и `ADMIN_PASSWORD` в окружении до того, как
открыть доступ (или сначала пройди визард через loopback, включив логин).
Доступный снаружи экземпляр без Google-ключей, логина и админа отвечает `503` на
всё: анонимный визард и single-user режим работают только на loopback. В
поставляемом `compose.yaml` стоит `EXPOSED_MODE=0` - это объявляет сеть OrbStack
доверенной и оставляет single-user режим; убери его, если сеть не только твоя.

Подробный GCP-разбор ниже нужен только чтобы получить эти два значения. Всё в
разделе [Конфигурация](#конфигурация) — опционально / для автодеплоя (env перебивает значения
из визарда).

## Google Cloud setup

1. Открой <https://console.cloud.google.com/apis/credentials>.
2. **Create credentials** → **OAuth client ID** → Application type **Web application**, имя `gsc-hub`.
3. Authorized redirect URIs:
   - `http://localhost:5173/auth/callback/google` (dev)
   - `https://your-domain.example/auth/callback/google` (только если будешь деплоить)
4. Включи **Search Console API** в том же проекте: <https://console.cloud.google.com/apis/library/searchconsole.googleapis.com>.
5. **OAuth consent screen** (теперь это **Google Auth Platform → Audience**): User Type — **External**. Дальше либо **Publish** (любой Google-аккаунт сможет залогиниться), либо оставь в **Testing** и добавь свои email-адреса в Test users.
6. Скопируй Client ID и Client Secret — вставь их в **setup-визард** при первом открытии приложения. `AUTH_SECRET` руками генерировать не нужно — визард создаёт и хранит его в SQLite.

`webmasters` у Google — «sensitive scope», но для personal-tier использования формальная verification не требуется (OAuth user cap допускает до 100 пользователей для неподтверждённых sensitive-scope). На consent screen увидишь предупреждение «unverified app», кликни **Advanced → Go to gsc-hub (unsafe)** чтобы продолжить. В redirect URI указывай только `http://localhost:5173/auth/callback/google` — `.local`-redirect Google не примет.

## Архитектура

```
[браузер] ──┬─ https://gsc.local (OrbStack proxy, TLS) ──┐
            └─ http://localhost:5173 (loopback, для OAuth)┴─> [SvelteKit (Node) :3000] ──> Google Search Console API
                                                                       │
                                                                       └──> ./data/gsc-hub.db  (только OAuth-токены)
```

Один Node-процесс. Один SQLite-файл. Таблицы создаются и мигрируют при старте:

| таблица | что хранит |
|---|---|
| `google_accounts` | OAuth-токены подключённых Google-аккаунтов |
| `users`, `sessions` | опциональный логин (argon2-хэши, серверные сессии) |
| `app_config` | настройки из setup-визарда и ключи сервисов (окружение главнее базы) |
| `api_keys` | ключи машинного API: sha256, префикс и область по сайтам |
| `hidden_sites`, `query_filters` | что ты скрыл: сайты и шаблоны мусорных запросов |
| `site_branded_keywords`, `site_dates` | brand-термины и даты создания сайтов |
| `site_events` | твои отметки на таймлайне (склейки и т.п.) |
| `indexnow_keys` | ключи IndexNow по сайтам |
| `url_inspection_cache`, `site_health` | кеш URL Inspection (12 ч) и внешних health-проверок |
| `magiclinks_purchases` | след покупок: какие пары «запрос + URL» куплены и у какого провайдера |

**Никакие аналитические данные GSC не сохраняются.** Любой запрос на `/properties`, аналитику по сайту и портфельную аналитику, `/dashboard`, query-history или CSV-экспорт идёт в Google; между тобой и API только кеш в памяти (до 60 минут, сбрасывается кнопкой **Refresh**). Цена - задержка загрузки на холодном кеше, пропорциональная числу активных сайтов.

### Auth.js custom signIn callback

Auth.js v5 настроен с кастомным `signIn` callback, который **вместо создания app-сессии апсертит профиль и токены Google в `google_accounts`** по `profile.sub`, потом возвращает `'/'` чтобы Auth.js сделал редирект без сессионной куки. Подключение Google-аккаунта и вход в хаб - разные вещи: OAuth-флоу Google только добавляет аккаунт Search Console, а опциональный логин хаба (`ADMIN_EMAIL`/`ADMIN_PASSWORD`, пользователи и роли) - отдельная серверная сессия. Без этого логина приложение работает в single-user режиме и доверяет loopback.

## Приватность и данные

- Ответы Search Analytics (запросы, клики, показы, позиции) никогда не пишутся на диск: они живут в памяти процесса до 60 минут и пропадают при рестарте.
- Две вещи из Search Console в SQLite всё же попадают: результаты URL Inspection (кеш на 12 часов, чтобы беречь дневную квоту) и, если покупаешь ссылки, купленные пары «запрос + URL» (чтобы таблицы striking их отмечали). При покупке эти запросы и URL уходят выбранному провайдеру.
- На диске - OAuth-токены и твои настройки, список таблиц в [Архитектуре](#архитектура). SQLite-файл лежит в `./data/` (gitignored); удали его, чтобы стереть всё.
- Исходящие вызовы - в API Google и только в то, что ты включил: Bing Webmaster и IndexNow (`BING_API_KEY`), серпмонитор (`SERP_MONITOR_URL`), сервисы покупки ссылок (их ключи) и проверка релизов на GitHub из браузера (`UPDATE_CHECK=off` её выключает). Никакой аналитики и телеметрии.
- Токены и ключи сервисов хранятся открытым текстом. Для локального single-user инструмента это допустимо; если выставляешь наружу за `127.0.0.1` - шифруй at rest. Исключение - ключи машинного API: хранится только их sha256.

## Деплой через Docker Compose + OrbStack

В репе есть `Dockerfile` (multi-stage, Node runtime) и `compose.yaml` под [OrbStack](https://orbstack.dev/) на macOS:

```bash
docker compose up -d --build   # собрать и поднять
docker compose logs -f gsc     # логи
docker compose restart gsc     # рестарт
docker compose down            # снести (данные в ./data сохраняются)
```

- Доступ на **`https://gsc.local`** через OrbStack-proxy (авто-TLS) — задаётся label'ом `dev.orbstack.domains`. Также работает `https://gsc.orb.local` (auto-домен по имени контейнера).
- `restart: unless-stopped` поднимает контейнер после ребута (OrbStack стартует с логином).
- Контейнер также биндит **`127.0.0.1:5173 → 3000`** (только loopback). Это нужно исключительно для OAuth: consent-flow идёт через `http://localhost:5173`, потому что Google не принимает `.local`-redirect. Этот адрес используй для подключения аккаунтов, а `https://gsc.local` — для повседневной работы.
- `.env` читается через `env_file`; секреты подставляются в рантайме через `$env/dynamic/private`, не вшиваются в образ.
- `./data` примонтирован bind-mount'ом, поэтому SQLite-хранилище токенов переживает пересборки и общее с `pnpm dev`.

**Про безопасность:** по умолчанию приложение работает в single-user режиме без логина, поэтому порт привязан только к `127.0.0.1` - в БД лежат OAuth-токены Google. Чтобы выставить его в сеть, включи встроенный логин (`ADMIN_EMAIL`/`ADMIN_PASSWORD`, см. выше); доступный снаружи экземпляр без него отказывается работать. Прокси перед ним (например, Cloudflare Access) - хороший дополнительный слой, но не замена логину. Добавь production callback URL в Google OAuth client.

## Обновление

### Как узнать, что вышла новая версия

В футере видна версия, на которой работает этот инстанс — `v0.8.0`, ссылкой на
описание изменений этого тега. На dev-хосте рядом показан коммит рабочего дерева
(`v0.8.0 · 3af8529`); внутри контейнера git отсутствует, поэтому там только тег.

Раз в 12 часов браузер спрашивает GitHub Releases API про свежий релиз. Если он
новее запущенного, над хедером появляется баннер для залогиненного пользователя:
**Доступна v0.9.0 — что нового** — ссылка на release notes, закрывается крестиком
по конкретной версии (следующий релиз покажется снова). Сервер наружу не ходит, в
БД ничего не пишет, ответ кэшируется в `localStorage` — значит 12 часов считаются
на браузер, а не на инстанс.

`UPDATE_CHECK=off` отключает проверку полностью; версия в футере остаётся.

### Обновление деплоя на Docker Compose

```bash
git pull
docker compose up -d --build
```

Данные не теряются: SQLite лежит в примонтированной `./data` (или в named-томе), а
не в образе. Миграции схемы применяются автоматически при старте.

### Обновление из исходников

```bash
git pull
pnpm install    # нужно только если менялись зависимости
pnpm dev        # или: pnpm build && HOST=127.0.0.1 ORIGIN=http://localhost:3000 node build/index.js
```

### Откат

```bash
git checkout v0.7.1
docker compose up -d --build
```

Откатить код безопасно, откатиться **через миграцию схемы** — нет: миграции едут
только вперёд. Перед серьёзным даунгрейдом скопируй `data/gsc-hub.db` в сторону.

### Для ИИ-агента

Детерминированная последовательность без интерактивных шагов. Запускать из корня
репозитория.

```bash
# 1. Что запущено сейчас (в контейнере нет git — читаем манифест)
docker compose exec -T gsc sh -c 'grep -m1 "\"version\"" /app/package.json'

# 2. Какой релиз самый свежий
curl -s https://api.github.com/repos/izzipizzy/gsc-hub/releases/latest | grep -m1 '"tag_name"'

# 3. Обновляемся, если различаются
git pull --ff-only
docker compose up -d --build

# 4. Проверка: тег в футере должен совпасть с тем, что вытянули
curl -sL http://localhost:5173/ | grep -o 'releases/tag/v[0-9.]*' | head -1   # -L: the app 303s to /login
docker compose logs --tail 30 gsc
```

Ожидаемый итог: шаг 4 печатает `releases/tag/<новая версия>`, а логи заканчиваются
строкой `Listening on http://0.0.0.0:3000` без стектрейсов. Если `git pull
--ff-only` упал — в чекауте есть локальные коммиты: остановись и сообщи, не сливай
и не ребазируй. Если упала сборка, продолжает работать предыдущий контейнер —
ничего не потеряно.

Версии — обычные теги `vMAJOR.MINOR.PATCH`. Само приложение сравнивает их
покомпонентно как числа, а всё, что не разбирается ровно в три числа (pre-release,
dev-сборка), считает «не новее» — применяй то же правило, если автоматизируешь
решение.

### Выпуск релиза (для мейнтейнера)

Работает только в приватном рабочем чекауте мейнтейнера: конфигурация публикации (`.publish.conf`, `.publicignore`) намеренно не входит в публичное дерево, поэтому в публичном клоне команды ниже упадут.

```bash
pnpm release 0.8.0   # бампает package.json и коммитит — тег не ставит, ничего не пушит
# дописать секции 0.8.0 в CHANGELOG.md / CHANGELOG.ru.md, закоммитить их
git push origin main
pnpm release-publish --dry-run 0.8.0   # только предпросмотр, ничего не пишет
pnpm release-publish 0.8.0
```

`release-publish` собирает публичное дерево, коммитит его потомком публичного
tip, тегает, пушит на GitHub и создаёт релиз. Если в дереве появился публичный
путь, которого раньше не было на публике, скрипт печатает список и hash
подтверждения и просит ввести этот hash перед тем, как что-либо запушить —
это единственный барьер между приватным файлом и публичным пушем, так что
список стоит прочитать. **Никогда** не выставляй `PUBLISH_CONFIRM=auto` для
настоящего релиза — это обходной путь только для тестов, он пропускает
проверку с одним предупреждением в stderr.

Футер берёт версию из `package.json`, поэтому именно бамп определяет, что апп о
себе сообщает. Тег версии создаётся при публикации релиза, на публичном релизном
коммите. Баннер у других людей сработает только когда для этого тега появится
**релиз на GitHub** — одного запушенного тега мало.
